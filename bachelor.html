Cable Route Planner

A decision-support prototype that lets production planners at a cable factory see the consequences of a routing choice before they commit to it. Built for Nexans Norway AS in Halden by a team of five.

The problem

Large cables are produced in long, continuous runs, and each run has to be routed through a fixed network of cable tracks, switches, junctions and storage baskets inside the factory. Choosing one track can make other tracks unreachable several steps away.

There was no digital tool for planning the cable routes. Route decisions relied on experience and walking the factory floor, and the old system gave no real-time picture: the planners could not see which tracks were free, occupied or blocked, or what their colleagues had already planned. Conflicts were often discovered late.

What we built

With no existing tool to build on, we started from scratch. After thorough research into how the factory's routing works and extensive planning, we built a full-stack prototype that combines production runs, track status and the physical routing rules in one interactive map:

  • The cable network is modelled as a graph of nodes and edges with direction-sensitive transition rules.
  • A hand-drawn, recognisable SVG map of the factory is connected to that graph through shared IDs.
  • Planners import production runs from an Excel export, get a recommended route for each run, can pick their own route by clicking two points on the map, and see it validated against the rules.
  • Booking a route updates availability, so later recommendations account for it.

My contribution

I led the front-end and visualisation sub-group, took the meeting minutes and shared the leadership tasks, and was group leader for a period before we moved that role to a teammate so I could focus on building. The interactive map

I drew the factory map in Adobe Illustrator and turned it into an interactive React component (about 11,000 lines of SVG and network-rule data). Every track, junction and basket in the SVG has the same ID as its node or edge in the back-end graph. That shared ID is what lets the front-end take an API response like "segment X is occupied" and colour exactly that piece of the map.

The map has three layers: a static visual layer that never changes, an overlay layer that shows status, recommendations and selections, and an invisible hit layer with wide click targets. State changes only touch the overlay, so the map stays stable and fast. It sits in a pan-and-zoom container for the dense areas.

Front-end features

  • Manual route picker: click two nodes on the map and get ranked route alternatives with distance and hop count
  • Production run panel and a calendar date filter for the imported runs
  • Booking ("Tildel") wired to the back-end, with an availability panel that updates afterwards
  • Booking conflicts surfaced in a notification panel
  • Map zoom controls, and a final visual refresh of the whole interface with design tokens
  • The typed TypeScript contract for the network data, so the map and the API stay in sync

Back-end work during integration

  • M3, the Excel importer: rewrote it for the planning system's real export format, with validation against the agreed column schema and a FastAPI router
  • M5, the pathfinder: distance-weighted pathfinding that lists the k shortest rule-compliant routes, used both for recommendations and for the manual route picker
  • Extended the junction transition rules (M6) and wired the importer and pathfinder into the recommendation endpoint

Result

The prototype works end to end: it renders the network, imports the real production export, recommends and validates routes, supports manual override and updates availability after bookings. Most of the Must-Have requirements were met. Browser-based file upload, per-segment capacity warnings on the map, persistent logging and a full draft-scenario mode were left as future work, and are documented as such in the thesis.

What I learned

  • A hand-made map beat an auto-layout graph library. Planners need to recognise their own factory; an abstract node diagram would have been technically easier but less useful.
  • Shared IDs are the contract. Keeping the SVG, the TypeScript types and the Python graph on the same identifiers made integration work, and any mismatch showed up immediately on the map.
  • Mock first, then real data. Building the front-end against mock data let us work in parallel; switching to the real Excel export exposed the edge cases.
  • Leading a group is a job of its own. Meeting minutes, follow-up and keeping five people moving took real time next to the code, and taught me to be clear about responsibilities from day one.
